# Checking a trait `impl` body loses the module's own impls and macro-generated defns

Reproduced with the `coil` on PATH, macOS arm64, 2026-07-29.

When the compiler checks an `impl` body, any same-module definition that the body
transitively needs is resolved in a scope that is missing:

1. the module's own trait `impl`s, and
2. top-level `defn`s that arrived through macro expansion (a `(do (defn …) (impl …))`
   returned by a macro, which is exactly what `derive-eq` emits).

Prelude impls still resolve, so `=` on `i64` works fine inside impl-reachable code. Only
same-module impls disappear.

## Symptom 1: nested dispatch through a helper

```sh
coil check docs/repro/impl-body-scope/bug-nested-dispatch.coil
```

```
error: in 'p9.other-same': 'p9.Val' does not implement 'Eq'
   --> bug-nested-dispatch.coil:11:5
   |
11 |     (= (load x) (load y))))
```

`Val` does implement `Eq`: `(derive-eq Val)` is on line 6. Delete the final line
(`(impl Eq Other …)`) and the file compiles. `other-same` is not edited by that deletion;
merely being *reachable from an impl body* is what breaks it.

## Symptom 2: dispatch directly in the impl body

```sh
coil check docs/repro/impl-body-scope/bug-direct-dispatch.coil
```

```
error: in 'coil.core.Eq$pa.Other$=': 'pa.Val' does not implement 'Eq'
```

Same cause, attributed to the synthesized method rather than to a user function.

## Symptom 3: a macro-generated free function is not merely un-dispatchable, it is invisible

```sh
coil check docs/repro/impl-body-scope/bug-derived-fn-invisible.coil
```

```
error: in 'p8.ty-same': call to undefined function 'Val-eq'
```

`Val-eq` is generated by `(derive-eq Val)` and resolves fine when called from `main` in the
same file. It stops existing only for a function reachable from an impl body. Symptoms 1 and
3 together are why I think impl bodies are checked against a pre-expansion or
pre-impl-registration snapshot of the module rather than the final one.

## What still works

```sh
coil run docs/repro/impl-body-scope/works-plain-helper.coil        # prints ok=1
coil run docs/repro/impl-body-scope/works-delegate-pattern.coil    # prints val = 1  ty = 1  tyne = 0
```

- `works-plain-helper.coil`: an impl body calling a helper that uses only metal ops.
- `works-delegate-pattern.coil`: the shape that survives. Real logic lives in plain
  top-level `defn`s (`val-eq`, `ty-eq`), and each `impl` is a one-line delegate to one of
  them. `ty-eq` is reachable from `impl Eq Ty` and calls `val-eq`, which is fine because
  `val-eq` only needs prelude impls (`=` on `i64`) and never a same-module one.

## Why it matters

The working shape inverts the natural way to write this. You would like `derive-eq` on a
struct plus a hand-written `(impl Eq Ty)` for the sum that contains it, and have the sum's
equality dispatch through the struct's. That is precisely what fails, so every type in a
module has to carry a parallel free function and the impl becomes decoration. Any module
with a small tower of types (a compiler's type representation, an AST, nested collections)
hits this immediately.

Found while writing an interned type lattice: `Ty` is a `defsum` with a `Val` struct
payload, and `(impl Eq Ty)` delegating to `ty-eq` made `Val`'s derived `Eq` vanish.
