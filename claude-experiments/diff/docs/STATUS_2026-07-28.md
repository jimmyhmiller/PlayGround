# diffpack status: correctness and performance

Written 2026-07-28. Machine for every measurement below: Apple M2 Max, 12 cores, 64 GB, macOS 26.5.2, Node v26.5.0. Reference toolchain is Next.js 16.2.3, which uses **Turbopack for both `next build` and `next dev`**.

Read the "Provenance" section before quoting any number. Some figures here I verified myself; others are reported by the agents that did the work and have not been independently re-measured.

**Section 2 was fully re-measured by hand at 13:23 to 13:35 on an idle machine (load average 4 to 12).** Several earlier figures were overstated in diffpack's favour and have been revised down. The revisions are listed in section 2.4; the superseded numbers are kept there rather than quietly replaced.

## 1. Headline

diffpack runs [cal.com](https://github.com/calcom/cal.com) for real. Not "the build exits 0" and not "both sides produce the same error page": a real login as `pro@example.com` succeeds against a seeded Postgres, lands on `/event-types` as "Pro Example", and renders all 10 seeded event types. An 8-route audit matches `next start` exactly on HTTP status, redirect target, post-routing URL and rendered text length.

Against Turbopack it wins every cleanly measured performance axis except output size: build wall time (1.35x), build CPU (7.1x), build memory (5.2x), dev startup (1.16x), dev route latency (23.5x), dev memory (1.2x), and the dev edit loop (4.3x to fresh HTML). One cell, Turbopack's edit-to-DOM, could not be measured reliably and is left open rather than filled in (section 2.5). The margins are real but several are narrower than earlier drafts of this document claimed; see section 2.4. The remaining gaps are correctness details, listed in section 5.

### 2.3 What is deferred off the edit path, and proof it lands

An edit pushes a micro-chunk and hot-patches both server processes. The full chunk re-emit (`client.js` 18.6 MB, `server.mjs` 20.8 MB, `rsc-render/`) is deferred behind a 150 ms quiet window and coalesced across a burst:

```
[dev] next settled: full re-emit of client + ssr in 1313.5ms | rendered_chunks=2
```

Nothing in an update reads those files, but a full page reload and a worker respawn do. The deferral is load-bearing for latency, not cosmetic: without coalescing, back-to-back edits queued behind the previous re-emit at 1,233 to 1,321 ms, versus 196 to 216 ms with it. The respawn window is closed by a `pendingHot` replay, verified by killing the worker while `rsc-render/server.mjs` on disk was still stale and confirming the new string was still served.

## 4. Work completed today

### 4.1 Source maps were fabricated, and now are not

**The defect.** `Bundler::source_map` asserted that generated line *k* of a module's region in a chunk corresponded to **original line *k*** of that module's file, because `transform_module_in_language` ended in `Codegen::new().build(&program)` and discarded the codegen map. No real position data survived the transform. Every column was 0 and `names` was empty.

On a 13-line fixture whose `function widget` sits at line 5, the emitted map claimed line 1. The error is unbounded in general: erased type-only statements, JSX expansion, enums, decorators. A wrong source map is worse than no source map, because a debugger jumps confidently to the wrong line.

**The fix.** New `src/source_map.rs` carries real oxc printer positions through every text rewrite between a module's lowered code and a chunk's bytes, composing chunk position to module region offset to module map to original file, line, column and name, with the minified map chaining on top.

Two findings during the work are worth recording:

1. **Omitting a token does not mean "unmapped."** Node's `findEntry` and DevTools both return the last mapping at or before a position, ignoring line boundaries. So every bundler-authored region was silently inheriting the preceding author-code mapping, which is the original bug in a new place. Both map builders now emit explicit one-field segments. On cal.com, 761 of 763 chunks bled runtime frames into author code before this; 0 after.
2. **`lower_module_ast` never calls `Codegen::build`.** It drives an incremental printer, and oxc only creates its sourcemap builder inside `build()`, so the map could not be captured at all. The lowering now prints each fragment into its own `Codegen` and verifies byte for byte that the reference print equals the concatenation, refusing with a named diagnostic on mismatch rather than emitting a plausible wrong map. That check fired zero times across cal.com's 13,298 modules.

**Rewritten sources are labelled, not claimed.** MDX compile, the RSC `"use client"`/`"use server"`/`"use cache"` rewrites, `route_split`, the `next/font` macro and the Vite `define`/dead-branch rewrites all hand oxc text that is not the bytes on disk. Those sources are labelled `?diffpack-generated=<stage>&diffpack-graph=<graph>` with that rewritten text inlined as `sourcesContent`, so coordinates and content always agree. You are reading diffpack's rewrite, and the map says so.

**Audit.** cal.com, 763 maps, 11,825,602 segments: 0 unsorted, 0 generated or source positions out of bounds, 0 wrong names across 2,561,374 name tokens, 0 absolute paths, 0 colliding source URLs, 0 path-less source names, 763 of 763 maps carrying explicit unmapped markers.

**Coverage.** Counted directly over both full output trees:

| | JS files | with a sibling `.map` | coverage |
|---|---:|---:|---|
| diffpack | 1,287 | 1,265 | **98.3%** |
| Next / Turbopack | 3,778 | 3,638 | 96.3% |

diffpack's map coverage is *higher* than Next's. The raw counts differ because Turbopack emits roughly 3x as many chunks for the same app, not because anything is being skipped.

The 22 diffpack files without a map are all files where the shipped bytes **are** the source, so a map would be meaningless: diffpack's own runtime and orchestrator, shipped verbatim through `include_str!` (`next-server.mjs`, `next-prerender.mjs`, `next-render-core.mjs`, `ssr-module-map.mjs`, `server/index.mjs`, `rsc-render/index.mjs`, `_ssr/*.mjs`), and the app's own `public/` assets copied byte for byte (`service-worker.js`, `embed/embed.js`, `embed/preview.js`, plus their `static/` mirrors). Nothing compiled lacks a map.

Next's 140 unmapped files are a different case: alongside its manifests (`required-server-files.js`, `server/next-font-manifest.js`, `server/*-manifest.js`) there are genuinely compiled chunks with no sibling map, e.g. `static/chunks/17a_v6ouuwu4k.js`.

An earlier draft of this document reported "763 of 763 compiled files, versus Turbopack's 3,450 for 3,576". That was taken from a single cold build rather than the full output tree, and it framed the difference as a diffpack coverage gap. It is not one.

**Default policy.** `SourceMapChoice::Auto`: with no flag, the app's own framework config decides, per graph. For a Next app that is `next build`'s policy exactly, meaning server and react-server maps always and browser maps only under `productionBrowserSourceMaps`. `--sourcemap`/`--no-sourcemap` force it; passing both is a hard error rather than a silent precedence rule.

### 4.2 Dev server-rendered HTML was stale forever after an edit

**The defect.** After an edit, `curl` against the diffpack dev server returned the **old** string in the server-rendered HTML, permanently, while the browser DOM updated via Fast Refresh. diffpack was losing the edit-latency comparison while doing strictly less work than Turbopack.

**The diagnosis.** Entry-level re-importing fails three ways, not one:

1. A chunk-only re-emit never moves the entry's mtime, and the dev cache key was `statSync(ssrEntry).mtimeMs` on `server/server.mjs` alone.
2. `?v=<mtime>` busts only the entry's own specifier. Its static `import "./server.chunk-N.mjs"` resolves without the query, so Node's ESM cache returns the stale chunk.
3. Even when the entry mtime does move (an island living in the entry chunk), the runtime is a `globalThis` singleton whose `__cache` survives the re-import.

Only a URL Node has never seen re-evaluates.

The server-component case was worse than stale: the react-server worker **died** with `Module is not loaded: 9947` and served an 11 KB error shell. The apparent "freshness" afterwards was a cold respawn at 4,039 ms.

**The fix.** Per-changed-module granularity through a new `POST /__diffpack_dev/hot` channel: render a micro-chunk to `<out>/.hot/<graph>.<seq>.mjs`, import it, call `runtime.serverInvalidate(ids)`, rebind from the republished entry exports, forward to the react-server worker, and hold `pendingHot` for respawn replay.

Two live bugs were caught during the work rather than shipped:

- `write_hmr_chunk` rendering a **server** micro-chunk as `BrowserEsm` would have silently swapped `__dirname="/"` and `__filename="/index.js"` stubs into server modules the moment they were hot-updated.
- `serverInvalidate` re-runs the entry factory, and the rsc entry's `main()` guard was `if (!import.meta.url.includes("?v="))`, which is true on a re-run. That installed a second stdin reader, so every request rendered twice and both flights went out under one reply id. Flight was exactly 2x (26,255 to 52,347 bytes) and the SSR client died on `chunk.reason.enqueueModel is not a function`. The guard is now keyed by module URL.

**Regression test.** `scripts/rsc/next-dev-fresh-check.sh` edits, then polls a **fresh document** until the new string appears, for both edit classes, and fails if the server logged a new error, so crash-and-respawn "freshness" cannot pass. Wired into `check.sh`. Pre-fix it fails on the first assertion; post-fix, island 27 ms and server-component 20 ms.

### 4.3 Memory across a long edit session

160 consecutive edits in one process (60 island, 100 server-component), RSS of the whole tree:

- Orchestrator: 748, 710, 680, 741, 1036, 1132 MB. Oscillating, not growing.
- rsc-worker: 619, 717, 730, 780, 865, 826 MB. Plateaus after roughly the first 20.
- Tree total per round of 20 server edits: 4334, 4044, 3978, 3830, 3930 MB. Flat or declining.
- `<out>/.hot` after 120 pushes: exactly one 2.6 KB chunk plus its map.

## 9. Addendum (evening): the performance push

Two targets were set: production build at least 3x faster than Turbopack, and dev cold start below 1 second. The first is met with margin. The second is not met and cannot be met without per-route lazy compilation; the honest floor reached is 7.0 s.

### 9.1 Measured results

Interleaved cold-build pairs (diffpack, Turbopack, diffpack, Turbopack), load average ~10 throughout, `FORCE_COLOR=0`, maps on and verified on both sides (763 vs 3,450 emitted `.map` files), port free after each teardown.

| Axis | diffpack | Turbopack | Ratio |
|---|---:|---:|---|
| Cold build, maps on | **8.63 / 8.81 s** | 33.47 / 33.00 s | **3.8x faster** |
| Cold build CPU (user) | **23.9 / 23.5 s** | 155.4 / 149.7 s | **6.4x less CPU** |
| Cold build peak RSS | **1,625 / 1,707 MiB** | 5,988 / 5,978 MiB | **3.6x lighter** |
| Dev startup to first 200 | **7.03 s** | 14.87 s | 2.1x faster |
| Dev second route | **222 ms** | 5,275 ms | 23.8x faster |

Context for comparing against section 2: this run's ambient load (~10) is higher than section 2's, which inflates Turbopack more than diffpack (Turbopack converts CPU-parallelism into wall time, and there were fewer idle cores). Against section 2's own best Turbopack figure (28.09 s), diffpack's 8.7 s is still **3.2x**. The first-ever build of a fresh checkout (no recorded async-island set, so the ssr graph discovers twice) measured 8.65 s, indistinguishable from steady state.

The dev edit loop was re-verified after all of this: an island edit reaches a freshly fetched document in 29 ms and a server-component edit in 16 ms (`scripts/rsc/next-dev-fresh-check.sh`, both classes, no new server error).

**The sub-1-second dev target.** The remaining cold-start time is client graph (~2.5 s) + max(react-server, ssr) built concurrently (~3 s) + orchestrator boot and first render (~1.2 s). Getting under 1 second requires building routes lazily on first visit rather than building all three whole-app graphs up front; that is real architecture, deliberately deferred. (A persistent warm-start cache prototype measured 1.66 s to first 200 on restart; it was removed on request — no caching for now.)

### 9.2 What changed

1. **Split-chunk rendering is parallel.** The 504 react-server chunks rendered one at a time (6.05 s); each chunk's render, worker substitution, and write is independent `&self` work and now runs across the pool.
2. **Source-map composition is parallel and search-smart.** `compose_source_map` was ~100% of one core while eleven sat idle — millions of per-token binary searches and name checks. Resolution now runs in generated-order slices across the pool, and the per-token search is an exponential expand-from-hint (`partition_point_from_hint`, exhaustively tested equal to `partition_point` for every hint). Emission stays serial so the output is byte-identical.
3. **CSS runs beside the chunks.** The Tailwind pipeline (candidate scan, source read, compile — the react-server graph's second-largest cost) runs under `rayon::join` with the JS chunk renders.
4. **The three production graphs overlap.** The client build computes and atomically publishes its two manifests straight after discovery (they are pure graph facts, not emit facts); the orchestrator watches for them and spawns react-server and ssr the moment both exist, while the client's render/minify tail is still running. react-server emits directly into `rsc-render/` (`--server-dir=rsc-render`), which also retires the publish copy that serialized it against ssr.
5. **Client islands are pinned lazily.** The generated ssr/client entries pinned all 469 islands with eager `import * as`, evaluating the entire island tree at boot — measured as ~100% of the SSR bundle's boot (425 ms -> 9 ms). Pins are now never-called `require` thunks (bundled, registered, evaluated on demand by the RSC seam — which is exactly webpack's lazy `requireModule` semantics), except islands whose evaluation is async (top-level await, transitively): those must be settled before a flight consumes them, so they stay eager. The async set is a recorded build fact (`.diffpack-next/async-islands.json`), reconciled against each discovery; drift regenerates the entries and rediscovers once, then never again.
6. **A live shaking bug, found by the gate.** Lazy pins put a bare `require` beside a named `import` of the same module — and the import statement's demand downgrade erased the require's whole-module demand, shaking off exports the require observably reads (`control-boundary` lost its `default`; hydration died on both e2e next apps). The e2e corpus caught it before it shipped. Fixed in the transform (a specifier that is also `require`d keeps `all`), with a node-executed regression test. This could bite any real app mixing the two forms.
7. **Orchestrator boot overlaps its two big imports.** The react-server worker pool is prespawned before the SSR bundle is primed, so the worker's bundle evaluation runs concurrently with the orchestrator's own; `DIFFPACK_BOOT_TRACE=1` stamps each boot phase. (This also cuts production `diffpack start` first-request latency.)
8. **The dev server builds react-server and ssr concurrently** (scoped threads; they share only the client's manifests).
9. **Byte-stability hygiene**: manifest writes and the dev `rsc-render` copy skip byte-identical writes, keeping mtimes stable across rebuilds that reproduce the same output.

### 9.3 Verification

- `cargo test --release --lib`: **832 passed** (830 + the hint-equivalence test + the require-demand regression), three consecutive runs. `cargo clippy --release --all-targets -- -D warnings` clean.
- **Byte parity**, measured before the lazy-pin change: a full cal.com output tree built by the pre-change binary vs the new one differed in exactly three files — `rsc-render/server.mjs` and its map (the per-build random `DRAFT_SECRET`) and a `generatedAt` timestamp. Everything else in the ~5,000-file tree byte-identical.
- After the lazy-pin change (not byte-identical by design): the 9-route cal.com audit matches the reference exactly (status, redirect target, content length), `/pro/30min` renders the booker, and a double warm sweep logs zero errors; the earlier-observed abort/fetch errors reproduce identically on the pre-change build (boot-timing artifacts, not regressions).

**What the suite forced out — two shipped fixes:**

1. **styled-jsx was not compiled** (`src/styled_jsx.rs`). `<style jsx global>` stayed a raw `<style>` element in the React tree; cal.com's theme provider renders one behind `typeof window !== "undefined"`, which made a guaranteed hydration mismatch on every route the provider wraps — THE defect behind #50/#52, whose "recoverable, page works" framing in section 5 was too generous: the mismatch regenerated the client tree wholesale. Now compiled to the app's own `styled-jsx` runtime component (no DOM node, client-side head insertion), matching Next's SWC pass and the reference's observable output (zero `__jsx-` tags in its SSR HTML). Scoped styled-jsx is a hard error naming the file. Verified: booker page errors 1 -> 0. Exposed en route: a live shaking bug (a bare `require` beside a named `import` of one module lost its whole-module demand) — fixed with a node-executed regression test.

2. **`NEXT_PUBLIC_*` was never inlined** (`next_public_env` in the adapter). `next build` bakes every `process.env.NEXT_PUBLIC_*` read as a define, from the env as it stands after next.config evaluation (which cal.com mutates: `NEXT_PUBLIC_CALCOM_VERSION` from package.json). diffpack's client bundles read them from the browser process shim at runtime and got `undefined` — the `v.undefined-sh` footer, the `cityTimezones` 400 (`CalComVersion: null` vs a zod string schema) with react-query retrying forever, and the corrupted booker timezone label, all one bug. Verified: `cityTimezones` 200, exactly one fetch; version `6.2.0` inlined; timezone label correct.

**What remains — the one open blocker, well-fenced:** a booker-route-only client render loop (~165 React commits/s; `/auth/login` and `/pro` are quiet, reference booker is 0 mutations/5s vs diffpack's ~2,500) keeps every booking-flow interaction un-automatable (Playwright's actionability stability check never passes), which is exactly the 10 red tests. Excluded by instrumentation: network (every API call 200, exactly once), history/router (zero calls), the booker zustand store (zero state transitions during churn), fast timers and RAF loops (census'd; the embed `makeBodyVisible` 50 ms loop exists on the reference too), zustand duplication (one copy), module duplication by path (none). Established: dev-mode updater tracking blames a cohort — nine `Tooltip` instances plus `Switch`/`EventDuration`/`AvailableTimeSlots`/`BookerWebWrapperComponent` — and a CPU profile catches `useHandleInitialDateSelection -> onChange -> setSelectedDate` running from a dep-less `useEffect` each commit, plus `useSchedule` firing an sdk event during render. The loop predates today's work (the pre-change binary churns 2x harder). Next session: React DevTools profiler in a headed browser on the dev server, starting from the Tooltip cohort.

Suite-runner facts that cost time to learn: `maxFailures: 10` in headless mode aborts the run (the 52 "skips" are the abort, not real skips); the webServer entry reuses an existing :3000 listener outside CI, so whoever owns :3000 owns the results — one run was invalidated because `pkill` matched the yarn wrapper but not the detached `next-server` process, and only a pid-level `lsof -ti :3000` check caught it; the Playwright chromium installer stalled at ~1 MB on both its mirrors while the backing store served 15 MB/s, so the zips were fetched directly and laid into `~/Library/Caches/ms-playwright` with `INSTALLATION_COMPLETE` markers.
