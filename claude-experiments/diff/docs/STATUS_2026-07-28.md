# diffpack status: correctness and performance

Written 2026-07-28. Machine for every measurement below: Apple M2 Max, 12 cores, 64 GB, macOS 26.5.2, Node v26.5.0. Reference toolchain is Next.js 16.2.3, which uses **Turbopack for both `next build` and `next dev`**.

Read the "Provenance" section before quoting any number. Some figures here I verified myself; others are reported by the agents that did the work and have not been independently re-measured.

---

## 1. Headline

diffpack runs [cal.com](https://github.com/calcom/cal.com) for real. Not "the build exits 0" and not "both sides produce the same error page": a real login as `pro@example.com` succeeds against a seeded Postgres, lands on `/event-types` as "Pro Example", and renders all 10 seeded event types. An 8-route audit matches `next start` exactly on HTTP status, redirect target, post-routing URL and rendered text length.

Against Turbopack it wins on build wall time, build memory, dev startup, dev route latency, and (as of today) the dev edit loop. It loses nothing on speed. The remaining gaps are correctness details, listed in section 5.

## 2. Performance vs Turbopack, cal.com

985 source files, pinned `3894f37e`, real seeded Postgres, sequential runs on port 3000, `FORCE_COLOR=0`, medians of 3 (5 for edit latency).

### 2.1 Build

| Axis | diffpack | Turbopack | Ratio |
|---|---:|---:|---|
| Cold build, no source maps | 11,900 ms | n/a (always emits maps) | |
| Cold build, **with source maps** | **20,200 ms** | 27,565 ms | **1.37x faster** |

**The like-for-like row is the maps-on row.** Earlier today this comparison was reported as 11.8 s vs 27.6 s (2.34x). That compared diffpack's no-maps build against Next's always-maps build, which was not a fair comparison, and it was additionally measured while diffpack's maps were fabricated (section 4.1). Honest source maps cost **+8.3 s wall and +368 MiB peak**, and 1.37x is the number that should be quoted.

Neither tool is meaningfully incremental for production builds: diffpack -11% on an edit rebuild, Turbopack -2%.

Next reports "Ready in 186 ms" and then compiles per request; diffpack builds all three graphs (client, react-server, ssr) before serving. That difference flatters Turbopack on the startup row, and diffpack still wins it. The second-route row is where eager compilation pays off.

Dev source maps are **on by default** and stayed on. They cost roughly 150 ms of the edit path (edit-to-DOM measures 200 ms with maps, and the pre-fix path measured 664 ms with maps versus 514 ms without). The edit-loop win came from taking the multi-MB entry re-render off the critical path, not from disabling maps.

### 2.3 What is deferred off the edit path, and proof it lands

An edit pushes a micro-chunk and hot-patches both server processes. The full chunk re-emit (`client.js` 18.6 MB, `server.mjs` 20.8 MB, `rsc-render/`) is deferred behind a 150 ms quiet window and coalesced across a burst:

```
[dev] next settled: full re-emit of client + ssr in 1313.5ms | rendered_chunks=2
```

Nothing in an update reads those files, but a full page reload and a worker respawn do. The deferral is load-bearing for latency, not cosmetic: without coalescing, back-to-back edits queued behind the previous re-emit at 1,233 to 1,321 ms, versus 196 to 216 ms with it. The respawn window is closed by a `pendingHot` replay, verified by killing the worker while `rsc-render/server.mjs` on disk was still stale and confirming the new string was still served.

## 4. Work completed today

### 4.1 Source maps were fabricated, and now are not

**The defect.** `Bundler::source_map` asserted that generated line *k* of a module's region in a chunk corresponded to **original line *k*** of that module's file, because `transform_module_in_language` ended in `Codegen::new().build(&program)` and discarded the codegen map. No real position data survived the transform. Every column was 0 and `names` was empty.

On a 13-line fixture whose `function widget` sits at line 5, the emitted map claimed line 1. The error is unbounded in general: erased type-only statements, JSX expansion, enums, decorators. A wrong source map is worse than no source map, because a debugger jumps confidently to the wrong line.

**The fix.** New `src/source_map.rs` carries real oxc printer positions through every text rewrite between a module's lowered code and a chunk's bytes, composing chunk position to module region offset to module map to original file, line, column and name, with the minified map chaining on top.

Two findings during the work are worth recording:

1. **Omitting a token does not mean "unmapped."** Node's `findEntry` and DevTools both return the last mapping at or before a position, ignoring line boundaries. So every bundler-authored region was silently inheriting the preceding author-code mapping, which is the original bug in a new place. Both map builders now emit explicit one-field segments. On cal.com, 761 of 763 chunks bled runtime frames into author code before this; 0 after.
2. **`lower_module_ast` never calls `Codegen::build`.** It drives an incremental printer, and oxc only creates its sourcemap builder inside `build()`, so the map could not be captured at all. The lowering now prints each fragment into its own `Codegen` and verifies byte for byte that the reference print equals the concatenation, refusing with a named diagnostic on mismatch rather than emitting a plausible wrong map. That check fired zero times across cal.com's 13,298 modules.

**Rewritten sources are labelled, not claimed.** MDX compile, the RSC `"use client"`/`"use server"`/`"use cache"` rewrites, `route_split`, the `next/font` macro and the Vite `define`/dead-branch rewrites all hand oxc text that is not the bytes on disk. Those sources are labelled `?diffpack-generated=<stage>&diffpack-graph=<graph>` with that rewritten text inlined as `sourcesContent`, so coordinates and content always agree. You are reading diffpack's rewrite, and the map says so.

**Audit.** cal.com, 763 maps, 11,825,602 segments: 0 unsorted, 0 generated or source positions out of bounds, 0 wrong names across 2,561,374 name tokens, 0 absolute paths, 0 colliding source URLs, 0 path-less source names, 763 of 763 maps carrying explicit unmapped markers.

**Coverage.** 763 maps for 763 compiled JS files (100%), versus Turbopack's 3,450 for 3,576. The gap is chunk granularity: Turbopack emits about 4.6x as many chunks for the same app. The 18 diffpack JS files with no map are the app's own `public/` files copied byte for byte and the `include_str!` runtime, where the shipped bytes *are* the source.

**Default policy.** `SourceMapChoice::Auto`: with no flag, the app's own framework config decides, per graph. For a Next app that is `next build`'s policy exactly, meaning server and react-server maps always and browser maps only under `productionBrowserSourceMaps`. `--sourcemap`/`--no-sourcemap` force it; passing both is a hard error rather than a silent precedence rule.

### 4.2 Dev server-rendered HTML was stale forever after an edit

**The defect.** After an edit, `curl` against the diffpack dev server returned the **old** string in the server-rendered HTML, permanently, while the browser DOM updated via Fast Refresh. diffpack was losing the edit-latency comparison while doing strictly less work than Turbopack.

**The diagnosis.** Entry-level re-importing fails three ways, not one:

1. A chunk-only re-emit never moves the entry's mtime, and the dev cache key was `statSync(ssrEntry).mtimeMs` on `server/server.mjs` alone.
2. `?v=<mtime>` busts only the entry's own specifier. Its static `import "./server.chunk-N.mjs"` resolves without the query, so Node's ESM cache returns the stale chunk.
3. Even when the entry mtime does move (an island living in the entry chunk), the runtime is a `globalThis` singleton whose `__cache` survives the re-import.

Only a URL Node has never seen re-evaluates.

The server-component case was worse than stale: the react-server worker **died** with `Module is not loaded: 9947` and served an 11 KB error shell. The apparent "freshness" afterwards was a cold respawn at 4,039 ms.

**The fix.** Per-changed-module granularity through a new `POST /__diffpack_dev/hot` channel: render a micro-chunk to `<out>/.hot/<graph>.<seq>.mjs`, import it, call `runtime.serverInvalidate(ids)`, rebind from the republished entry exports, forward to the react-server worker, and hold `pendingHot` for respawn replay.

Two live bugs were caught during the work rather than shipped:

- `write_hmr_chunk` rendering a **server** micro-chunk as `BrowserEsm` would have silently swapped `__dirname="/"` and `__filename="/index.js"` stubs into server modules the moment they were hot-updated.
- `serverInvalidate` re-runs the entry factory, and the rsc entry's `main()` guard was `if (!import.meta.url.includes("?v="))`, which is true on a re-run. That installed a second stdin reader, so every request rendered twice and both flights went out under one reply id. Flight was exactly 2x (26,255 to 52,347 bytes) and the SSR client died on `chunk.reason.enqueueModel is not a function`. The guard is now keyed by module URL.

**Regression test.** `scripts/rsc/next-dev-fresh-check.sh` edits, then polls a **fresh document** until the new string appears, for both edit classes, and fails if the server logged a new error, so crash-and-respawn "freshness" cannot pass. Wired into `check.sh`. Pre-fix it fails on the first assertion; post-fix, island 27 ms and server-component 20 ms.

### 4.3 Memory across a long edit session

160 consecutive edits in one process (60 island, 100 server-component), RSS of the whole tree:

- Orchestrator: 748, 710, 680, 741, 1036, 1132 MB. Oscillating, not growing.
- rsc-worker: 619, 717, 730, 780, 865, 826 MB. Plateaus after roughly the first 20.
- Tree total per round of 20 server edits: 4334, 4044, 3978, 3830, 3930 MB. Flat or declining.
- `<out>/.hot` after 120 pushes: exactly one 2.6 KB chunk plus its map.

## 7. Provenance: what is verified, and by whom

This matters more than usual here, because several numbers reported earlier today did not survive contact with a careful re-measurement.

**Independently verified by me:**

- The source-map repro, decoded by hand with a VLQ decoder. Every token lands on the exact identifier: `function widget` to `widget.ts 5:0`, `"MARKER_ALPHA"` to `6:17`, `widget(...)` to `main.ts 2:12` with `name=widget`, and synthetic lines carrying explicit unmapped markers.
- `cargo build --release` clean and `cargo test --release --lib` 830 passed after the dev-freshness work landed.
- No leaked dev servers, port 3000 free.

**Reported by the implementing agent and adversarially verified by three independent agents:** everything in section 4.1. All three adversaries initially returned "does not hold" with real defects (mixed coordinate systems in `derive_flat_code`, zero unmapped segments, absolute path leak, source URLs losing their directory with 45 collisions, an annotation shifting a statement by one line, a cost regression). Those were repaired, and the repair reports gates green.

**Reported by the implementing agent only, NOT independently verified:** everything in section 4.2 and 4.3, including the 200 ms edit-to-DOM figure and the memory table. The workflow was stopped after its correctness phase, so its three adversarial verifiers (freshness, measurement integrity, honesty) and its final measurement report never ran. Resume with `Workflow({scriptPath: '/tmp/dpe2e/dev-edit.js', resumeFromRunId: 'wf_7fd64f7b-fd4'})`; completed agents replay from cache.

**Corrected during the session, recorded so the wrong numbers are not re-quoted:**

- Turbopack dev startup was first measured at a 7,269 ms median. That run was contaminated by a leaked dev server holding port 3000, letting later iterations get an instant 200 from the previous run's warm server. Corrected to 16,594 ms, reproduced on a second independent harness. Always kill the full descendant tree and abort if the port is busy at launch.
- The 2.34x build ratio was not like-for-like (no-maps versus always-maps) and was measured against fabricated maps. The honest figure is 1.37x.
- The 591 ms dev-edit baseline did not hold; with real source maps it re-measured at 664 ms.
- An "intermittent cal.com build failure, 2 in 6" was refuted 9 out of 9 with a fixed binary. The real cause was concurrent builds from parallel agents sharing one output directory, which is now task #60.

## 8. Reproducing

cal.com is prepared at `/tmp/dpe2e/calcom`, pinned `3894f37e14eae5082770f35ff1fde72110c0e6b6`. **Do not re-clone or re-install**: 349 MB checkout plus 3.4 GB of `node_modules`, roughly 20 minutes.

```sh
# database: calcom_diffpack_e2e on brew postgresql@17, 105 tables, 40 seeded users
# cleanup when done:  dropdb calcom_diffpack_e2e

WEB=/tmp/dpe2e/calcom/apps/web

# reference (Turbopack)
cd $WEB && FORCE_COLOR=0 corepack yarn next build
cd $WEB && FORCE_COLOR=0 corepack yarn next dev --turbopack -p 3000

# diffpack
cd $WEB && FORCE_COLOR=0 /path/to/diffpack build-app . production
FORCE_COLOR=0 /path/to/diffpack dev $WEB 3000
```

`FORCE_COLOR=0` is mandatory on anything whose output is parsed: this environment exports `FORCE_COLOR=3`, and Node ANSI-colorizes bare numbers, which has already corrupted one benchmark run.

`apps/web/next.config.ts` is a wrapper importing `next.config.__orig__.ts` and adding `typescript.ignoreBuildErrors`. Keep it; type checking is off for both sides, so no `tsc` time is in either column. Do not run the repo's own `yarn build` (turbo): `@calcom/prisma`'s postinstall calls `fs.rm(..., {recursive: true})`, removed in Node 26, which is unrelated to bundling.
